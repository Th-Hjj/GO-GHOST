# Prompt 08 — 独立验收审查

**Astra 思考档位：ultra。请在客户端选择；本文件不修改客户端配置。**

先读取并遵守：
- 当前适用的 AGENTS.md、工程协作规则；
- Docs/GO_GHOST_VS/Execution_Contract.md；
- Docs/GO_GHOST_VS/GO_GHOST_Design_Baseline_ZH.md；
- Docs/GO_GHOST_VS/Prototype_Test_Profile.md；
- Docs/GO_GHOST_VS/Implementation_Log.md（若存在）。
需要核对 Macro 时，读取同目录原表或 Macro_Readable_Extract.md；不要从旧 README 推断新玩法已实现。
只执行本阶段，按 Execution_Contract 的格式交付，完成后停止。

你是本次新会话中的独立验收审查者。不要把前一个代理说“完成了”当作证据。
本阶段只审查，不修改源码、资产、配置或修补问题；可在现有权限下运行不会改写项目源码/资产的现有检查。

读取最新设计、执行约束、TEST 方案、当前实际代码/Scene/Prefab/构建入口，以及阶段测试日志。
优先检查项目是否真的证明：
成立的 Boss 战→真实失败与下一位接替→有意义的配装选择→下一场差异→与获胜配置对应的结果。

重点找跨系统漏洞：
- 首次直接获胜是否依赖失败后才初始化的配置/结果 UI。
- 每次 New Game 是否真恢复第一位 0%，而不是继承上局 AI 配装。
- 死亡是不是只是旧角色重载而没有下一位警察身份；Boss 伤害/弹体/事件有没有跨尝试残留。
- 配装锁是不是仅靠隐藏 UI；胜利读取的是否其实是编辑草稿或可变的共享资产。
- AI 接管是否会被别的脚本/设置抢回；是否偷偷自动开火/移动或暗改伤害。
- 武器是否被纳入分母或百分比；是否把三件全装 60% 误写成 100%。
- 同一百分比是否因为脑模块/历史/死亡/武器不同而映射到不同结果。
- 高改造是否被擅自写成坏结局，或未确认的故事/功能混入提交。
- 两招 Boss 是否存在结构上无法靠基础动作应对的攻击；不要用代码阅读替代真人难度评价。
- “测试通过”是否实际只跑了静态扫描/强制胜败；独立构建是否真的启动过。

输出：
A. 阻止试玩的问题（崩溃/卡流程/核心规则错误）；
B. 可以试玩但会污染结论的问题（预警不清、AI收益不明显、反馈不足等）；
C. 不阻止本次 slice 的后续事项。
每个确认问题给真实位置、违反的规则、复现方法/证据和最小修复建议；不确定则标“待验证”，不编造行号或运行结果。
不要用风格偏好凑出大规模重构清单。

最后明确：
- 可以进入真人 playtest；
- 或可以试玩但须注意列明限制；
- 或仍被具体问题阻塞。
若没有实际运行/构建证据，不能无条件宣布可试玩。
有问题交回 FIX prompt；不在审查中偷偷改代码。

## 你验收后再推进
新会话审查实际代码与测试证据，确认是否真的适合交给真人试玩。
